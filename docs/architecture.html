QualiForge AI Overview Architecture

How QualiForge AI is built

Four services on one internal server, one database, and hosted services for AI models and tracing. The design is sized for a team of 10 and a builder with 20 hours a week, and leaves room to grow without a rewrite.

Based on the architecture decisions of 13 November 2026.

The first workflow: story to tests

The workflow is a fixed path, not agents deciding among themselves what to do next. Steps that need judgement use AI; steps that touch Jira are plain code.

    FETCH["Fetch the story from Jira"]
    KNOW["Add approved team knowledge"]
    ANALYZE["AI: analyse the requirement"]
    DESIGN["AI: design tests"]
    REVIEW["AI: review tests"]
    OK{"Review passed?"}
    HUMAN{"QA engineer reviews each test"}

    OK -->|"No, at most twice"| DESIGN
    OK -->|"Yes, or with warnings after two tries"| HUMAN
    HUMAN -->|"Regenerate with feedback"| DESIGN
    HUMAN -->|"Approved tests"| CREATE
    HUMAN -.->|"Edits, rejections, feedback"| LEARN
    CREATE --> DONE

Safeguards

  • AI cannot change Jira. The AI agents have no tools that write anything. Only a plain-code step, after a person approves, creates tests. This also defends against instructions hidden in retrieved or uploaded documents.
  • No duplicate tests. Each test carries a unique key. If a run is retried, only the tests not yet created are created.
  • Everyone signs in. Members and administrators. Without sign-in, anyone on the network could start runs or change stored credentials, and approvals would have no author.
  • Credentials are protected. Only administrators can enter Jira and Confluence credentials. They are encrypted, never shown again after saving, and hidden in traces.
  • Runs stay visible if tracing is down. Every step is also saved in the database, so the run list and run page work without Langfuse.
  • Agents cannot loop. The reviewer can send tests back at most twice, which caps time and cost.

How the design changed after review

The first proposal described a general platform with nine services. Two independent reviews, by Claude and Gemini, recommended cutting it down to fit the team and the builder. The owner adopted most of the Claude review and selected points from Gemini.

Topic First proposal Decided
Order of work Build the knowledge layer first Rebuild the working workflow first, then add knowledge
Services Nine, including Redis, Prometheus and Grafana Four: web, API, worker, database
Run queue Redis A table in the existing database
Monitoring OpenTelemetry, Prometheus, Grafana Langfuse for AI runs; container health checks and logs

All decisions

Each decision records a reason and the condition that would make us revisit it. Open one to read it.

ADR-001Web app built with Next.js
Decision
Next.js with TypeScript, used only for screens. It talks to the API through a client generated from the API's specification.
Why
A second backend would need to be kept in sync. The generated client breaks the build if the two sides disagree.
ADR-002One Python backend with FastAPI
Decision
All Python code in one package, started two ways: as the API and as the worker.
Why
One person cannot maintain many packages, and both share the same data models.
ADR-003Workflows are fixed paths in LangGraph
Decision
Each workflow is a fixed graph. No agent chooses another agent. The reviewer can send tests back at most twice, then the run goes to a person with the reviewer's warnings.
Why
A run can wait days for approval without holding a worker. The cap stops agents from looping and spending tokens.
Revisit when
The rebuilt workflow scores worse than today's and the gap cannot be closed.
ADR-004One database: PostgreSQL
Decision
PostgreSQL holds business data, the search index (pgvector and full-text search), and the workflow engine's internal state, kept in separate tables.
Why
One database to run and back up.
Revisit when
The index reaches millions of entries or search gets slow.
ADR-005No Redis; the queue is a table
Decision
Runs are queued in a database table that one worker checks. The web app refreshes run status every few seconds.
Why
Ten users start a few runs at a time.
Revisit when
More than about 20 runs happen at once, or the refresh delay becomes a complaint.
ADR-006Search is added only where it helps
Decision
A known record, such as the selected story, is fetched directly. Search is only for finding related content, from an approved list of Jira projects and Confluence spaces, re-indexed nightly. It is built in step 4, where the measurements show a gap.
Why
Shared credentials leave no per-user permissions to filter, and Atlassian Cloud cannot notify a server on the internal network.
Revisit when
Teams with different access rights share the platform, or nightly updates are not fresh enough.
ADR-007Langfuse Cloud is the only tracing tool
Decision
Langfuse Cloud (US region) provides traces, tokens and cost, prompt versions, the evaluation set, and release comparison. Each run links to its trace. Self-hosting is decided later.
Why
It already solves two of the three problems the platform exists for. Building the same screens would duplicate it.
Condition
Traces contain story text and tests and leave the internal network. Accepted by the owner on 13 November 2026. Self-hosting would need more memory than the current server has.
ADR-008No server dashboards for now
Decision
Prometheus and Grafana are deferred. Container health checks and logs are used.
Revisit when
Someone other than the builder operates the system, or outages go unnoticed.
ADR-009Document upload: Markdown and text PDFs
Decision
Uploaded documents go to S3-compatible storage, added in step 4. Markdown and text-based PDFs first. Scanned PDFs are refused with a clear message.
Revisit when
Users need scanned documents or other file types.
ADR-010Docker Compose on one internal server
Decision
The first setup has web, API, worker and database.
Why
It matches the server and the team size.
ADR-011Reviewer corrections become team knowledge
Decision
An edit, rejection or feedback, with its reason, becomes a proposed knowledge item. Approved items are added to later runs for their project or component. Each item records its author, status, version and origin. The existing skills are the starting content.
Why
This is the main reason for the platform: corrections should build up as shared knowledge instead of prompt edits.
Revisit when
There are too many items to add by project or component.
ADR-012Tests are created as Jira Test issues
Decision
Each approved test becomes a Jira issue of type Test, linked to the story, with steps in the description in one fixed template. Labels record the platform, AI provider and model; the description records the run and the approver.
Why
It avoids a second API in the first version. The fixed template allows a later move to Xray.
Revisit when
The team needs Xray test steps or test sets.
ADR-013Approval is per test
Decision
Reviewers edit tests in place, choose which to create, and approve, regenerate with feedback, or reject. Both the original and the edited test are kept. Waiting time is not counted in run duration.
Why
A yes-or-no for the whole batch forces reviewers to throw away good tests. The stored edits feed team knowledge.
ADR-014Only approved, plain-code steps write to Jira
Decision
AI steps have no write tools. Each test has a unique key, so a retry creates only what is missing.
Why
It is the practical defence against hidden instructions in documents, and against duplicate tests after a restart.
Revisit when
Never.
ADR-015Local accounts, two roles
Decision
Members and administrators. Administrators can promote others. The last administrator cannot be removed. Sign-in sits behind one function so it can be swapped later.
Revisit when
The company provides single sign-on.
ADR-016Jira and Confluence credentials
Decision
Entered by administrators on a settings page, encrypted, never shown again, hidden in traces, with a test-connection button. The page warns that every user can see what the credentials can see.
Revisit when
Per-user access to Jira and Confluence is required.
ADR-017One AI provider plus a fallback
Decision
The standard model interface from the LangGraph ecosystem, with no custom layer or proxy. Cost figures come from Langfuse.
Revisit when
Per-team budgets or central key control are needed.
ADR-018Today's workflow is the bar to beat
Decision
Before rebuilding, the current Claude workflow is traced and scored on 20 to 30 real stories with the tests the team accepted. The rebuild must score at least as well, and the set is re-run for every release.
Why
Without it, nobody can show the rebuild is as good as today, or that a release is better than the last.
ADR-019Versions come from git and Langfuse
Decision
An agent's version is the code commit plus the prompt version, both recorded on each run. No registries yet.
Revisit when
Non-developers need to change agents or workflows.
ADR-020Order of work
Decision
Baseline, walking skeleton, feedback loop, uploads and search, then more workflows. See the plan.
Why
Each step ends with something people can use and removes one risk.
Revisit when
The baseline or the walking skeleton fails its check.

QualiForge AI Overview Architecture

Turn Jira stories into reviewed test cases, and let every review improve the next run.

QualiForge AI is an internal application for our QA team. AI agents draft test cases from a Jira story. A QA engineer approves, edits or rejects each one, and the approved tests are created in Jira. The corrections are kept as team knowledge, so the agents get better without anyone rewriting prompts.

Stage: design. No platform code has been written yet.
Page updated 27 November 2026, from the decisions of 13 November 2026.

Why we are building it

The first workflow already exists. A Claude coding agent with a set of skills turns a Jira story into reviewed test cases today. It works, but only as a personal tool, and it has four limits:

  • It runs on one machine

    Only the person who set it up can run it.

  • Nobody can see inside a run

    There is no record of what the agent did, why, or what it cost.

  • Releases cannot be compared

    Nothing shows whether a change made the tests better or worse.

  • Corrections are lost

    The only way to improve it is to edit its instructions by hand. What reviewers fix is not kept anywhere.

QualiForge AI turns that tool into a shared application that fixes all four. The last one, turning corrections into team knowledge, is the main reason the platform exists.

What the first version does

  • Start a run from the browser

    Pick a Jira story and start the workflow. No local setup.

  • Follow every run

    See which runs are complete, running or waiting for approval. Open a run to see each step, and follow a link to the full trace with tokens and cost.

  • Review one test at a time

    Edit a test in place, then approve it, reject it, or ask for a new version with feedback. One weak test no longer sinks the whole batch.

  • Approved tests appear in Jira

    Each becomes a Jira Test issue linked to the story, written to one fixed template and labelled with the AI model that wrote it.

  • A knowledge base the team owns

    Edits, rejections and feedback become proposed knowledge items. Once approved, an item is used in later runs for its project or component.

  • Proof that a release is better

    A fixed set of 20 to 30 real stories, with the tests the team accepted, is re-run for every release and scored.

  • Accounts and roles

    Everyone signs in. Administrators manage accounts and the Jira and Confluence connection.

  • Later: uploads and search

    Upload Markdown and text PDF documents, and search Confluence and existing tests, starting with spotting duplicate tests.

How a run works

  1. A QA engineer picks a Jira story and starts a run.
  2. The platform fetches the story and adds the approved team knowledge for its project.
  3. Three AI agents work in a fixed order: one analyses the requirement, one designs tests, one reviews them. The reviewer can send the tests back at most twice.
  4. The run pauses until a QA engineer reviews each test. The pause can last days without holding anything up.
  5. Approved tests are created in Jira. A retry never creates a duplicate.
  6. Every edit, rejection and piece of feedback becomes a proposed knowledge item.

The AI agents can only read and draft. They have no way to change Jira; only the final step, after a person approves, writes anything. The architecture page shows this as a diagram.

Plan

Each step ends with something people can use and removes one risk before the next step starts.

  1. Baseline Next

    Record how well today's Claude workflow performs on 20 to 30 real stories. Every later release must score at least as well.

  2. Walking skeleton

    Accounts, the connection settings page, the run list and run page, the workflow rebuilt on the platform, per-test approval, and safe creation of tests in Jira.

  3. Feedback loop

    Reviewer corrections become knowledge items that the team reviews and approves. The story set is re-run for every release.

  4. Uploads and search

    Upload documents, and index Confluence and existing tests, starting with duplicate detection.

  5. More workflows

    Analysis of existing test cases first. Generating Playwright tests and unit tests comes after, once generated code can run in an isolated sandbox.

What stakeholders should know

  • Data leaves the internal network. Story text and generated tests are sent to external AI providers and to Langfuse Cloud, a hosted tracing service in the US. The project owner accepted this on 13 November 2026. Whether company policy allows it is still to be confirmed.
  • Everyone sees the same Jira and Confluence content. The platform connects with one shared set of credentials, so every user can see whatever those credentials can see.
  • It is built by one person. One SDET, about 20 hours a week, working with AI coding assistants. The design is kept small on purpose.
  • It runs on one internal server. 16 GB of memory and 100 GB of disk, for a team of 5 to 10 people.

Not part of the first version

  • Use by other companies, or by more than about 10 people.
  • Writing tests through the Xray API, or adding them to Xray test sets. Tests are plain Jira Test issues for now.
  • Company single sign-on. There is no company identity provider yet.
  • Scanned PDFs, which would need text recognition.
  • Generating Playwright or unit test code.

Each item has a stated condition that would bring it back. See the architecture page.
